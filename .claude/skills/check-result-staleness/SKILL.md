# 分析結果の陳腐化検出

`data/output/**/*_results.json` が、今の入力ファイルとコードから作り直しても同じになる状態か（陳腐化していないか）を判定し、結果を GitHub Issue で報告するスキル。報告 Issue は 1 件に保ち、前回からの差分をコメントで追記する。

検出と報告のみを行い、分析の再実行・結果ファイルの修正は行わない。

判定は [check_result_staleness.py](../../../scripts/check_result_staleness.py) が決定的に行う。**5分類の定義・優先順位・既知の限界・終了コードはスクリプト冒頭の説明を正本とし、本ファイルに再掲しない**。本スキルは報告 Issue の特定・前回状態の保存・スクリプトの実行・終了コードに応じた書き込みを担う。

## 実行モードの判定

呼び出し元のプロンプトに「自動実行」である旨の明記がある場合は**自動実行**、それ以外は**対話実行**として扱う。

- **自動実行**: ユーザーへの確認を行わず、下記「状況別の動作」に従って書き込む
- **対話実行**: 判定結果を提示し、GitHub への書き込み（起票・コメント・close）は**本文を提示してユーザーの確認を得てから**行う

いずれのモードでも、書き込むのは `main` をチェックアウトしている場合だけである（下記）。

判定の基準は、実行時にチェックアウトされている `HEAD` と作業ツリーの `data/output/` である。

### main 以外のブランチでは書き込まない

最初に Bash ツールで `git branch --show-current` を実行する。結果が `main` でない場合（空＝detached HEAD を含む。worktree の作業ブランチもここに当たる）は、実行モードによらず **GitHub に書き込まない**。

- **対話実行**: Step 1・2 を行わず、Step 3 を報告モードの引数（`--report-output`・`--previous-issue-json`）なしで実行して判定結果だけを提示する。Step 4・新規起票は行わない。Step 5 では「`main` 以外（{ブランチ名}）のため書き込まなかった」と、作業ブランチのコード・結果で判定した旨を添える
- **自動実行**: 定期実行のプロンプトが冒頭で見送るため通常は起こらない。起きた場合は何も実行せず、見送った旨を報告して終了する
- `--data-root` で `main` のチェックアウトを指しても書き込まない。`--data-root` で変わるのは入力の基準だけで、走査する結果 JSON とコードの比較基準（`HEAD`）は作業ブランチのままのため、`main` の状態と一致する保証が無い

報告 Issue のマーカーは前回の判定結果の正本であり、次回の実行はこれとの差分を出す。作業ブランチの判定（git 管理外の入力が無いための「入力欠落」など）を書き込むと、次回の `main` での実行で偽の「解消」「分類変化」が報告される。スクリプトも報告モードを `main` 以外では拒否する（終了コード 1）。

## 実行手順

GitHub への書き込みの本文は、[../shared/github-project-api.md](../shared/github-project-api.md) の「日本語テキストの安全な処理」に従い、一時ファイル経由の `--body-file` で渡す。`gh` の出力も一時ファイル経由で UTF-8 として読む。一時ファイルの置き場所はセッションのスクラッチパッドとする（以下 `{スクラッチパッド}`）。

### Step 1: 報告 Issue の特定

**Bash ツールで実行する**（PowerShell のリダイレクトは出力の文字コードを変え、JSON を壊すおそれがあるため）:

```bash
gh issue list --state open --label analysis --limit 100 \
  --json number,title,body,createdAt > "{スクラッチパッド}/staleness_issues.json"
```

`gh` が非0の終了コードで終わった場合（認証切れ・ネットワーク断など）は、以降の手順を行わず、書き込まずに終了してエラーを報告する（保存ファイルが空のまま「報告 Issue なし」と読むと、報告 Issue を重複して起票してしまうため）。

次の 3 条件をすべて満たす OPEN の Issue を報告 Issue とする（本ファイルに特定の Issue 番号は書かない）。

- タイトルが「analysis: 分析結果の陳腐化検出報告」で始まる
- `analysis` ラベルが付いている
- 本文にスクリプトが付ける Issue 用フッタ（`ISSUE_FOOTER`）の文言「このIssueは /check-result-staleness スキルにより作成されました」を含む

OPEN の報告 Issue が複数ある場合は `createdAt` が最新のものを採用し、他の番号は報告の中で列挙して集約を促す（自動では close しない）。

### Step 2: 前回状態の保存（報告 Issue がある場合のみ）

```bash
gh issue view {番号} --json body,comments > "{スクラッチパッド}/staleness_issue.json"
```

`gh` が非0の終了コードで終わった場合（認証切れ・ネットワーク断など）は、以降の手順を行わず、書き込まずに終了してエラーを報告する。

前回の問題の一覧は、本文・コメントの末尾にスクリプトが埋め込む不可視のマーカー（`<!-- result-staleness-state: ... -->`）からスクリプトが復元する。**マーカーを手で編集・削除しない**（マーカーが無いと前回状態を復元できず、スクリプトは終了コード 1 で止まる）。

### Step 3: 判定と報告本文の生成

プロジェクトルートから `python -m` 形式で実行する。Python は conda 環境 `masterresearch` の python.exe をフルパスで呼ぶ（Claude Code のツールからは `conda activate` が使えず、`python` が別の Python を指すことがあるため）。報告 Issue がある場合だけ `--previous-issue-json` を付ける。

```sh
python -m scripts.check_result_staleness \
  --output-json "{スクラッチパッド}/staleness.json" \
  --output-md "{スクラッチパッド}/staleness.md" \
  --report-output "{スクラッチパッド}/staleness_report.md" \
  --previous-issue-json "{スクラッチパッド}/staleness_issue.json"
```

- 入力の GeoPackage は git 管理外のため、作業ツリーに無ければ「入力欠落」になる。対話実行で別の作業ツリーの入力を使って判定したい場合に限り `--data-root {その作業ツリーのルート}` を付ける（入力は読み取りだけに使われる。`main` 以外のブランチでは、付けても書き込みは許されない）
- 既定の監視パス（スクリプトの `DEFAULT_WATCH_PATHS`）以外に監視したいコードがあれば `--extra-watch-path {パス}` を付ける

### Step 4: 状況別の動作

| 報告 Issue | 終了コード | 動作 |
|---|---|---|
| なし | 0（問題あり。起票本文を書き出した） | 下記「新規起票」 |
| なし | 3（問題なし） | 書き込まない。「問題なし」と報告する |
| あり | 0（前回から差分あり） | `gh issue comment {番号} --body-file "{スクラッチパッド}/staleness_report.md"` で差分コメントを追記する |
| あり | 3（差分なし） | GitHub には書き込まない。「前回から変化なし」と報告する |
| あり | 4（全件解消） | 差分コメント（解消一覧）を追記したのち `gh issue close {番号} --reason completed` で close する |
| — | 1（判定できない・報告 Issue を読めない・`main` 以外で報告モードを実行した） | 書き込まない。標準エラーの内容を報告する |

- 「差分」は、新規に問題になった結果・解消した結果・問題のまま分類が変わった結果のいずれかがあること（継続中の問題だけなら差分なし）
- 全件解消で close する際、他にも OPEN の報告 Issue があれば、その番号を報告の中で列挙する（次回はそれが採用されるため）
- 報告 Issue のタイトルの日付は**初回起票日のまま変更しない**（最終確認日は差分コメントの見出しで分かる）

### 新規起票

```bash
gh issue create \
  --title "analysis: 分析結果の陳腐化検出報告 (YYYY-MM-DD)" \
  --label "analysis" \
  --body-file "{スクラッチパッド}/staleness_report.md"
```

本文（判定結果・マーカー・Issue 用フッタ）はスクリプトが書き出したものをそのまま使い、編集しない。この Issue は検出結果の報告を目的とするため、優先度のユーザー確認・プロジェクトへの追加は行わない。

### Step 5: 報告

- 行った書き込み（新規起票／差分追記／close／書き込みなし）と、その URL または書き込まなかった理由を報告する
- `{スクラッチパッド}/staleness.md` の分類別の件数を添える
- 「要再実行（コード変更）」のうち、理由が「記録コミットがローカルに無い」ものは、コードが変わったのではなく生成時のコードを確かめられない状態である（スクリプト冒頭の既知の限界）。その件数を分けて添える。この理由が付くのは、来歴にコードのハッシュ（`provenance.code`）を持たない旧形式の結果か、ハッシュの記録が無い監視パスがある場合に限る
- **対話実行**のみ: 「要再実行」の結果が残っていれば、再実行するかをユーザーに確認する（再実行の要否・順序は研究者が判断する。本スキルは再実行しない）

## 注意事項

- GitHub への書き込みは、上記「状況別の動作」の起票・コメント・close だけとする。リポジトリへのコミット・push は行わない
- 分析を作り直して保存済みの結果と一致するかの確認（再現性チェック）は、本スキルの範囲外である。[check_reproducibility.py](../../../scripts/check_reproducibility.py) を対象構成を指定して実行する（対象構成は `scripts/reproducibility_targets.json` に書く）

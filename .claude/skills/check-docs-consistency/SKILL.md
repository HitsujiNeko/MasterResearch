# ドキュメント整合性チェック

`docs/` 配下のMarkdownドキュメント群について、CLAUDE.md・docs/README.mdで定義された
「Single Source of Truth」運用ルールが守られているかを検査し、問題点と修正案を
レポート形式で提示するスキル。

**重要**: このスキルは検出とレポート作成のみを行う。ファイルの修正は、レポート提示後に
ユーザーが承認した項目のみ、個別にEdit toolで適用する。一括の自動修正は行わない。

---

## チェック項目

### 1. docs/README.md カタログとの差分

- `docs/README.md` の「📊 全ドキュメントカタログ」テーブルに記載されているファイルパス一覧を抽出する
- `docs/` 配下の実際の `.md` / `.mmd` ファイル一覧（`04_archive/01_metadata/papers_database.csv` 等のCSVは対象外）と比較する
- 検出する差分:
  - 実ファイルは存在するがカタログに未掲載（掲載漏れ）
  - カタログに記載があるが実ファイルが存在しない（削除済み・改名済みの可能性）
  - `docs/README.md` のディレクトリ構造図（```構造```ブロック）とも矛盾していないか確認する

### 2. リンク切れチェック

- `docs/` 配下の全 `.md` ファイルから Markdown リンク `[テキスト](パス)` を抽出する
- 外部URL（`http://`, `https://`）は対象外。相対パスのみ検査する
- リンク先パスが、リンク元ファイルからの相対パスで実在するか確認する（`#見出し`等のアンカーは無視してパス部分のみ確認）
- `.github/` 配下や `src/` 配下への相対リンクも同様にファイル存在確認する

### 3. メタ情報の有無チェック

- `docs/README.md` のルールでは、新規ドキュメントの冒頭に以下を記載することを推奨している:
  ```markdown
  **最終更新**: YYYY-MM-DD
  **関連ドキュメント**: [xxx.md], [yyy.md]
  ```
- `docs/` 配下の各 `.md` ファイル（README.md自身とテンプレート類 `04_archive/templates/` を除く）について、
  **ファイル冒頭の見出し（`# タイトル`）から数行以内（目安5行以内）** に「最終更新」の記載があるかを確認する
  - ファイル末尾や本文中（変更履歴・作成日メモなど）の日付記載は「冒頭メタ情報あり」と判定しない
  - 例: S7/S8のように文末に作成日情報があるだけのファイルは「未記載」として報告する
- 記載がないファイルを一覧化する（※即修正は提案しない。記載が定着していない既存ファイルも多いため、
  「未記載一覧」として報告し、追記するかどうかはユーザーの判断に委ねる）

### 4. 用語の表記揺れチェック

CLAUDE.mdの最小用語集に基づき、以下の表記揺れを `docs/` 全体から検索する:

- **LST単位**: 「℃」「°C」「度C」「ケルビン」「K」などLST関連箇所での単位表記の揺れ
  - CLAUDE.mdの規約上は「°C」に統一されるべき
- **シナリオ名**: 「Satellite Only」「Limited」「Full」の表記揺れ（大文字小文字、日本語訳との混在など）
- **座標系**: 「WGS84」「EPSG:4326」「VN-2000」の表記揺れ・誤記
- **RQ表記**: 「RQ1」「RQ2」「RQ3」の表記揺れ（"RQ 1" のような半角スペース混入など）

ここでは「規約と異なる表記が使われている箇所」を一覧化するに留め、文脈上意図的な表記
（例: 引用文中の表記、他研究の用語）は除外候補として注記する。

### 5. 内容レベルの整合性チェック（同一対象の表記不一致）

文書間で同一の対象（EPSG番号、データセット名、ファイル名、UTMゾーン名など）が
異なる名称・値で記載されていないかを確認する。

- **EPSG/CRSコードと地域名・ゾーン名の対応**:
  例: 「EPSG:5897」に対して文書Aでは「UTM Zone 48N相当」、文書Bでは別のゾーン名が
  記載されている、といった対応関係の不一致を検出する
  - `docs/` 内でEPSGコード（`EPSG:\d+`）を検索し、各コードに付随するゾーン名・地域名・
    用途説明を文書ごとに比較する
- **データセット名・ファイル名の不一致**:
  例: 同じデータソースを指して「BSHorizon DEM」「BS Horizon」のように表記が異なる、
  あるいは実際のファイル名と文書中の記述が異なる
- **数値・選定結果の不一致**:
  例: `dem_selection_guide.md` でのDEM選定結果（採用DEM名）が、参照元の
  `calc_urban_params_guide.md` 等で異なるDEM名として記載されている、といった
  選定結果の伝播漏れ
- EPSG/CRSコードの対応関係チェックは必須（grepで`EPSG:\d+`を抽出し機械的に比較する）
- データセット名・数値・選定結果の不一致チェックは、項目1〜4の実施中に
  気づいた範囲でベストエフォートで報告する（網羅的な全文比較は行わない）

検出した不一致は「どちらが正しいか」を断定せず、両方の記載箇所と内容を提示し、
どちらに統一するかをユーザーに確認する。

## 実行手順

1. **対象ファイル一覧の取得**

   ```powershell
   Get-ChildItem -Path docs -Recurse -Include *.md,*.mmd | Select-Object -ExpandProperty FullName
   ```

2. **docs/README.md の読み込みとカタログ抽出**

   `docs/README.md` の「📊 全ドキュメントカタログ」セクション内の各テーブルから、
   Markdownリンク `[ファイル名](パス)` を抽出してパス一覧を作る。

3. **各チェックの実施**

   上記チェック項目1〜5を順に実施する。リンク切れチェックは `docs/` 配下に限定せず、
   ドキュメントから `src/`・`.github/` への参照も含めて確認する。

4. **レポート作成**

   検出結果を以下の形式でユーザーに提示する（ファイルには保存せず、会話内で出力する）:

   ```markdown
   ## ドキュメント整合性チェック結果

   ### 1. docs/README.md カタログ差分
   - 掲載漏れ: ...
   - 実ファイルなし: ...

   ### 2. リンク切れ
   - {ファイル}:{行} → `{リンク先}` (存在しない)
   - ...

   ### 3. メタ情報未記載
   - {ファイル}
   - ...

   ### 4. 用語表記揺れ
   - {ファイル}:{行} 「{検出表記}」→ 規約表記「{正規表記}」?
   - ...

   ### 5. 内容の不一致（同一対象の表記・記述差異）
   - 対象: {EPSGコード/データセット名など}
     - {ファイルA}:{行}: {記載内容A}
     - {ファイルB}:{行}: {記載内容B}
   - ...
   ```

   各項目について、検出件数が0であれば「問題なし」と明記する。

5. **修正の提案と適用**

   レポート提示後、検出された項目について修正案（具体的な編集内容）を提示し、
   ユーザーに「どの項目を修正するか」を確認する。

   - ユーザーが承認した項目のみ、Edit toolで個別に修正する
   - `docs/README.md` のカタログ更新が必要な場合は、`docs/README.md` のルール
     （ディレクトリ構造図・カタログテーブル・ドキュメント関係図・変更履歴）に従って追記する
   - 用語の表記揺れ修正は、引用文・固有名詞・他研究由来の表記など意図的なものを誤って
     書き換えないよう、各箇所をユーザーに確認してから修正する
   - 一括 `replace_all` による表記統一は、誤検出のリスクがあるため使用しない

---

## 注意事項

- このスキルは `docs/` 配下を対象とする。`README.md`（ルート）や `CLAUDE.md` 自体の
  整合性確認が必要な場合はユーザーに目的を確認する
- ファイル数が多い場合、リンク切れチェックや用語検索は Grep / Glob を活用し、
  個別にファイルを全文Readすることは避ける
- 検出のみで終わるタスクであっても、最後に「次にどうするか（修正対象の選択）」を
  ユーザーに確認して終了する

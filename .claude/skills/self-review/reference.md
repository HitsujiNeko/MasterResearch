# セルフレビュー 詳細リファレンス

**役割**: `/self-review` スキルの点検セクションの詳細項目・所見出力テンプレートを定義する。
**関連**: [SKILL.md](SKILL.md), [CodingRule.md](../../docs/02_methods/CodingRule.md)（点検項目の正本）

点検項目そのものの正本は CodingRule.md 側にある。本ファイルは CodingRule.md を土台に、
**セルフレビュー時に確認する形へ具体化**したチェックリストと出力様式を提供する。
CodingRule.md と矛盾する記述は置かない（矛盾を見つけたら CodingRule.md 側を正とする）。

---

## 1. 自動検出不可のプロジェクト固有規約

`ruff`・`markdownlint` で機械保証されない項目。CodingRule.md「13. ツールによる自動チェックの範囲 →
セルフレビューで確認する項目（自動検出不可）」および「15.2 実装後チェック」に対応する。

### Python

- [ ] コメント・docstring が**日本語**で記述されている
- [ ] 追加・変更した関数に日本語 docstring と型ヒントが付与されている
- [ ] 複雑な処理に日本語コメントが過不足なく付与されている
- [ ] **日本語変数名を使っていない**（識別子は英語スネークケース、クラスはキャメルケース）
- [ ] ファイルヘッダーが module docstring 形式に一本化されている
- [ ] 研究データの**絶対パスをハードコードしていない**（相対パス・`pathlib.Path` を使用）
  - 例外: 外部ツール（QGIS 等）の探索パスは許容（CodingRule.md 7章の条件に従う）
- [ ] 再現性に影響する設定（パス・乱数シード・閾値）が明示されている
- [ ] 例外処理が実装され、エラーメッセージが日本語で理解しやすい
- [ ] 不要なコード・未使用変数・デバッグ出力を残していない

### Markdown / ドキュメント

- [ ] コードフェンスに言語指定がある（MD040）
- [ ] 記法が統一されている（バッククォート・`**太字**`・ATX 見出し・リストマーカー）
- [ ] 同一内容を複数ファイルに重複記載していない（docs/README.md が唯一の真実の情報源）

> Markdown の多くは `markdownlint` で機械保証されるため、ここでは lint が拾わない
> 「重複記載」「言語指定漏れの見落とし」等を重点的に確認する。

## 2. 変更差分の妥当性

- [ ] 変更が Issue の要件・完了条件に対応している
- [ ] 要件外の想定外な変更（無関係なファイル・設定変更・デバッグ出力）が混ざっていない
- [ ] 共通化すべきロジックを `src/common/` に配置する構成規約に沿っている
      （汎用的な重複コード検出は `/code-review` に委譲。ここでは配置規約への適合のみを見る）
- [ ] 変更ファイルを自分で読み返し、規約違反がないことを確認した

## 3. テスト保証範囲の点検

**「テスト通過＝正しい」ではない**。テストが検証**していない**範囲を明示的に列挙し、
「テスト通過が担保していないこと」として言語化する。各項目にリスクの高さ（高/中/低）を添える。

### 一般的な非保証範囲

- [ ] 未検証の入力: 想定外の型・空・欠損値・巨大データ・文字化けを含む入力
- [ ] 境界値: 範囲の上限・下限・0・負値・オーバーフロー
- [ ] 異常系: 不正値・例外経路・ファイル不在・ネットワーク失敗
- [ ] 副作用: ファイル出力・状態変更・外部サービス（GEE 等）呼び出しの結果検証有無
- [ ] 暗黙の前提条件: 呼び出し順序・事前状態・グローバル設定への依存

### 研究ドメイン固有の非保証範囲（本研究の前提）

- [ ] **CRS**: 入出力が WGS84（EPSG:4326）基準か。面積・距離計算で投影座標系を使っているか。
      VN-2000 データの変換が正しいか
- [ ] **単位**: LST が必ず**摂氏（°C）**で扱われているか（K・ケルビン残存がないか）
- [ ] **有効カバレッジ**: 有効域を ROI 全体と同一視していないか（信頼できる範囲の明示）
- [ ] **分析シナリオ**: Satellite Only / Limited / Full の使用データ範囲が混在していないか

> これらはテストで機械的に担保しにくく、かつ研究結果の妥当性に直結するため、
> 「テストが緑でも未検証」である点をユーザーに明示することに価値がある。

## 所見出力テンプレート

点検結果は以下の様式で提示する。**問題なしの観点も「対応不要」として明示**し、網羅性を示す。

```markdown
## セルフレビュー所見（コミット単位: {変更の要約}）

対象差分: {ファイル名の一覧}

### 対応要（修正を推奨）

1. [{カテゴリ}] {ファイル}:{行} — {指摘内容}
   - 根拠: {CodingRule.md の該当項目 / 要件 / 前提}
   - 提案: {推奨する対応}

### 任意（判断はユーザーに委ねる）

1. [{カテゴリ}] {ファイル}:{行} — {改善余地の内容と理由}

### テスト保証範囲の所見

- テストが担保していないこと: {未検証の入力・境界・副作用・ドメイン前提}（リスク: 高/中/低）

### 対応不要（点検済み・問題なし）

- {確認した観点}: 問題なし
```

- カテゴリ例: `規約`（固有規約）/ `妥当性`（差分）/ `テスト非保証`（テスト範囲）
- **修正はこの提示では実施しない**。ユーザーが採否を判断し、承認された指摘のみ修正してからコミットする。

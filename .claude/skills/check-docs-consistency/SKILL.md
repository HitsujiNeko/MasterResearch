# ドキュメント整合性チェック

`docs/` 配下のドキュメント群が CLAUDE.md・docs/README.md の「Single Source of Truth」運用ルールに従っているかを検査し、問題があれば GitHub Issue として報告するスキル。報告 Issue は 1 件に保ち、前回からの差分をコメントで追記する。

検出と報告のみを行い、ファイルの修正は行わない。

機械的に判定可能な項目（カタログ差分・リンク切れ・メタ情報の有無・用語の表記揺れ・書誌整合・鮮度）は `src/doc_checks/` にスクリプト化され、PRごとにCIジョブ `doc-consistency` として実行される。本スキルはその実行結果の確認と、意味的判断を要するチェックを担う。

---

## チェック項目

1. **機械的チェック（CI結果の確認）** — `python -m src.doc_checks.run_all` を実行し、カタログ差分・リンク切れ・メタ情報・表記揺れ・書誌整合・鮮度の検出結果を取得する
2. **事実レジストリの逐件照合** — `references/check_spec.md` の事実レジストリ**全件**を、正本と写しで行（箇所）単位に照合する。照合対象の項目・レジストリ・判定基準はすべて `references/check_spec.md` を正本とする（項目一覧を本ファイルに再掲しない）
3. **結果数値の再突合** — `docs/03_results/` の各文書の数値を、生成元データ（各文書本文の出力ファイル節が指す JSON/CSV）と再照合する。手順は `references/check_spec.md` を参照

---

## 実行手順

1. `python -m src.doc_checks.run_all` を実行する
2. 事実レジストリの逐件照合を実施する（`references/check_spec.md` の 1 章。Grep / Glob を活用し、不要な全文 Read は避ける）
3. 結果数値の再突合を実施する（`references/check_spec.md` の 2 章）
4. 既存の報告 Issue を特定し、「前回の指摘一覧」を復元する（下記「報告 Issue の特定」）
5. 今回の結果と前回の指摘一覧を比較し、状況に応じて報告する（下記「状況別の動作」）

GitHub への書き込み（起票・コメント・close）の本文は、[../shared/github-project-api.md](../shared/github-project-api.md) の「日本語テキストの安全な処理」に従い、一時ファイル経由の `--body-file` で渡す。`gh` の出力を読む場合も一時ファイル経由で UTF-8 として読む。

### 実行モードの判定

呼び出し元のプロンプトに「自動実行」である旨の明記がある場合は**自動実行**、それ以外は**対話実行**として扱う。

### 報告 Issue の特定

```bash
gh issue list --repo HitsujiNeko/MasterResearch --state open --label docs \
  --limit 100 --json number,title,body,createdAt > {一時ファイルパス}
```

次の 3 条件をすべて満たす OPEN の Issue を報告 Issue とする（本ファイルに特定の Issue 番号は書かない）。

- タイトルが「docs: ドキュメント整合性チェック報告」で始まる
- `docs` ラベルが付いている
- 本文に下記「新規起票」の Issue 用フッタ文言を含む

OPEN の報告 Issue が複数ある場合は `createdAt` が最新のものを採用し、他の番号は報告の中で列挙して集約を促す（自動では close しない）。

### 前回の指摘一覧

採用した報告 Issue の本文とコメントを取得する。

```bash
gh issue view {番号} --repo HitsujiNeko/MasterResearch \
  --json body,comments > {一時ファイルパス}
```

報告 Issue に本スキルの差分コメント（下記「差分コメントの様式」のコメント用フッタで識別する）があれば、**最新の差分コメントの「新規」＋「継続」**を前回の指摘一覧とする。差分コメントが無ければ Issue 本文の指摘を前回の指摘一覧とする。差分コメントには継続中の指摘を毎回すべて載せるため、最新のコメント 1 件で現状を復元できる。

指摘が同一かどうかは「対象ファイル＋対象項目（事実レジストリの項目名・リンク先・対象の数値等）」で判定し、行番号のずれだけでは別の指摘としない。本スキル以外によるコメント（ユーザーの補足等）は前回の指摘一覧に含めないが、対話実行時は内容をユーザーに提示する。

### 状況別の動作

| OPEN の報告 Issue | 今回の結果 | 動作 |
|---|---|---|
| なし | 問題なし | 何も書き込まず、「問題なし」と報告して終了する |
| なし | 問題あり | 下記「新規起票」 |
| あり | 前回から差分あり（新規または解消が 1 件以上、かつ未解消が残る） | 報告 Issue に差分コメントを追記する |
| あり | 差分なし（新規・解消とも 0 件） | 自動実行時は何も書き込まない。対話実行時はユーザーに「前回から変化なし」と報告のみ行う |
| あり | 全件解消（今回の問題が 0 件） | 解消一覧を差分コメントとして追記したのち close する |

全件解消時の close:

```bash
gh issue close {番号} --repo HitsujiNeko/MasterResearch --reason completed
```

報告 Issue のタイトルの日付は**初回起票日のまま変更しない**（最終確認日は差分コメントの見出しで分かる）。

### 新規起票

`.github/ISSUE_TEMPLATE/docs-consistency-report.md` の構成に従い Issue を作成する。

```bash
gh issue create --repo HitsujiNeko/MasterResearch \
  --title "docs: ドキュメント整合性チェック報告 (YYYY-MM-DD)" \
  --label "docs" \
  --body-file {一時ファイルパス}
```

末尾に以下の Issue 用フッタを追加する:

```markdown
---
🤖 このIssueは /check-docs-consistency スキルにより作成されました。
```

この Issue はチェック結果の報告を目的とするため、優先度のユーザー確認・プロジェクトへの追加は行わない。

### 差分コメントの様式

各項目の書式は `.github/ISSUE_TEMPLATE/docs-consistency-report.md` の各節の書式（`{ファイル}:{行}` と内容）に揃え、該当する節名（カタログ差分・リンク切れ等）を項目の先頭に添える。該当なしの節は「なし」と書く。

```markdown
## 整合性チェック差分報告 (YYYY-MM-DD)

### 新規

- 

### 解消

- 

### 継続

<!-- 前回から残っている指摘を全件載せる（前回の指摘一覧の復元に使うため省略しない） -->

- 

### 推奨アクション（新規分）

- 

<!-- OPEN の報告 Issue が複数ある場合のみ: 他の OPEN の報告 Issue の番号を列挙し、集約を促す -->

---
🤖 このコメントは /check-docs-consistency スキルにより追記されました。
```

```bash
gh issue comment {番号} --repo HitsujiNeko/MasterResearch --body-file {一時ファイルパス}
```

### 次のアクション

- **対話実行**: 行った書き込み（新規起票／差分追記／close／書き込みなし）を報告し、未解消の指摘が残っていれば「このまま修正に着手しますか？」と確認する
- **自動実行**: 状況別の動作に従った書き込み（または書き込みなし）で完了とする

---

## 注意事項

- 検査対象の中心は `docs/` 配下だが、事実レジストリの照合では正本・写しとして
  ルート `README.md` と `CLAUDE.md`（最小用語集が複数事実の正本）も**読み取り対象に含む**（読み取りのみ・修正はしない）。
  レジストリ照合以外の目的でルートファイル自体を検査する場合は、ユーザーに目的を確認する

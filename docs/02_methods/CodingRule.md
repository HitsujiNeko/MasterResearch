# コーディング・ドキュメント記法規約（研究プロジェクト用）

**最終更新**: 2026-06-27  
**関連ドキュメント**:  

- AI指示書 → [CLAUDE.md](../../CLAUDE.md)
- 実装例 → [src/gee/gee_calc_LST.py](../../src/gee/gee_calc_LST.py)

**適用範囲**: プロジェクト内のすべてのPythonスクリプト（1〜13章）、すべてのMarkdownドキュメント（14章）

---

本ドキュメントは、研究プロジェクトにおけるコードとドキュメントの品質・一貫性を確保するための規約です。Pythonコードは PEP 8 に準拠し、Markdownドキュメントは markdownlint によるルールに従います。

`ruff`（`ruff check` + `ruff format`）および `markdownlint` による自動検査を導入しているが、自動で検出できない項目（日本語コメント・docstringの必須化、日本語変数名の禁止、ファイルヘッダー形式など）も含むため、コミット前のセルフレビューは引き続き必要（[13. ツールによる自動チェックの範囲](#13-ツールによる自動チェックの範囲)を参照）。

---

## 1. 命名規則

- **変数名・関数名**：英語で意味のある名前を付ける（例：`calculate_mean`、`data_frame`）。日本語変数名は使用しない。
- **クラス名**：単語の先頭を大文字にしたキャメルケース（例：`DataAnalyzer`）。
- **定数**：全て大文字、単語間はアンダースコア（例：`MAX_COUNT`）。

## 2. インデント・空白

- インデントは**半角スペース4つ**。
- タブは使用しない。
- 演算子の前後、カンマの後にはスペースを入れる。
- 上記は `ruff format` により自動整形される。

## 3. 型ヒント

- 関数の**引数・戻り値には原則として型ヒントを付与**する。
- 標準的な型は `pathlib.Path`、`list[str]`、`dict[str, Any]` などPEP 585以降の組み込みジェネリクスを使用する。
- 引数・戻り値のないシンプルな`main()`関数にも `-> None` を付与する。

## 4. コメントの書き方

- **日本語で記述**し、簡潔かつ分かりやすく。
- 初心者にも理解できるように丁寧に説明する。
- コードの意図や処理内容、注意点を明記する。
- 関数やクラスには**ドキュメンテーションストリング（docstring）**を必ず付与。

### コメント例

```python
# データフレームから欠損値を除外する
cleaned_df = df.dropna()
```

## 5. 関数・クラス設計

- 1関数1責務を意識し、処理を分割する。
- 関数には必ず**docstring**を付け、引数・戻り値・処理内容を日本語で記述（Googleスタイル準拠）。
- クラスも同様にdocstringを付与。
- **引数を持たない関数**では、docstringの`Args`セクションを省略する（「Args: なし」のような記述はしない）。

### docstring例

```python
def calculate_mean(values: list[float]) -> float:
    """
    平均値を計算する関数

    Args:
        values: 計算対象の数値リスト
    Returns:
        平均値
    """
    return sum(values) / len(values)
```

## 6. ファイルヘッダー

- ファイル先頭は**module docstring**のみとし、概要・用途・依存関係などを日本語で記述する。
- `# 作成者: ...` `# 作成日: ...` のような行コメントは付与しない（作成者・作成日は `git log` で確認できるため）。

## 7. パスの扱い・再現性

- 入出力パスは**相対パス**・`pathlib.Path` を用いる。
- **研究データの絶対パス（ユーザー名やドライブ直下の研究データディレクトリなど）はハードコードしない**。
- 例外として、**外部ツールの実行ファイル探索パス**（QGIS同梱の`ogr2ogr.exe`など、OS環境に依存するインストール先）は、フォールバック候補のリストとして絶対パスを記述してよい。
- 乱数を使用する処理では、必ずシードを設定する。

## 8. コーディングの基本方針

- 情報の**正確性**と**一貫性**を重視する。
- 再現性のあるコードを書く。
- 例外処理（try-except）を適切に行う。

## 9. エラー処理

- 予期しないエラーに備え、適切な例外処理を実装する。
- エラーメッセージは日本語で分かりやすく記述する。

## 10. 使用ライブラリ

現在`environment.yml`に含まれる主なライブラリ（2026-06時点）：

- **データ分析**：NumPy、Pandas、Matplotlib
- **地理空間データ処理**：Geopandas、Shapely、Fiona、Rasterio、PyProj
- **衛星画像解析**：Google Earth Engine API（earthengine-api）
- **機械学習・統計**：Scikit-learn、SHAP

これは現状の一覧であり、ライブラリ選定を制限するものではない。実装内容に応じて最適なライブラリを選定してよい。`environment.yml`に含まれないライブラリが必要な場合は、追加前にユーザーの承認を得てから`environment.yml`に追加する。

`environment.yml` を環境構築の正本とし、手順は [../setup.md](../setup.md) に記載する。  
`requirements.txt` は参照用であり、環境構築の起点にはしない。

## 11. テスト方針

- テストフレームワークは `pytest` を使用し、`tests/` 配下に `test_*.py` として配置する。
- GIS処理スクリプトには、小規模なサンプルデータに対して処理が正常終了し、期待するレイヤー・カラム・CRSを持つ出力が生成されることを確認する**スモークテスト**を推奨する。
- 出力するCSV/JSONについては、想定するカラム名・キーが存在するかを確認する**スキーマ検査**を推奨する。
- 全ての処理を網羅するテストは必須としないが、回帰を防止したい主要な処理には最低限のテストを用意する。

## 12. その他

- コードは定期的に見直し、リファクタリングを行う。
- 不要なコードや使われていない変数は削除する。

## 13. ツールによる自動チェックの範囲

`ruff`・`markdownlint` で機械的に保証される項目と、セルフレビューで確認する項目を区別する。

### ruffで保証される項目（Python）

- PEP 8準拠（インデント・空白・行長など）
- import順序（isort相当）
- 未使用のimport・変数
- `ruff format` によるフォーマット統一

### markdownlintで保証される項目（Markdown）

- コードフェンスの言語指定（MD040）
- 見出しレベルの連続性（MD001）
- 記法の統一（コードフェンス記号・強調・太字のスタイル）
- 空白・改行の整合性（末尾スペース、連続空行、タブ禁止など）

### セルフレビューで確認する項目（自動検出不可）

- コメント・docstringの日本語記述、必須箇所への付与
- 日本語変数名の禁止
- ファイルヘッダー形式（module docstringへの一本化）
- 絶対パスの扱い（研究データパス禁止／外部ツール探索パスの許容）
- 再現性（乱数シード、相対パス）

## 14. ドキュメント記法ルール（Markdown）

`markdownlint`（VS Code 拡張 + pre-commit フック）による自動チェックを導入している。ルール設定は `.markdownlint.json` に定義されている。

### コードフェンスの言語指定（MD040）

コードフェンス（` ``` `）には**必ず言語名を指定**する。言語指定がないとレビューツール（CodeRabbit 等）で警告される。

よく使う言語名:

| 言語名 | 用途 |
|---|---|
| `python` | Pythonコード |
| `bash` | シェルコマンド（Linux/macOS） |
| `powershell` | PowerShellコマンド（Windows） |
| `json` / `jsonc` | JSON / コメント付きJSON |
| `yaml` | YAML設定ファイル |
| `markdown` | Markdownの記法例 |
| `text` | 出力例・ディレクトリ構成など言語に該当しないもの |
| `csv` | CSV形式データ |
| `sql` | SQLクエリ |
| `bibtex` | BibTeX文献情報 |

### 記法の統一ルール

- コードフェンス記号はバッククォート（`` ` ``）に統一する（`~~~` は使用しない）
- 強調は `*斜体*`、太字は `**太字**` に統一する（`_斜体_`、`__太字__` は使用しない）
- 見出しは `#`（ATXスタイル）に統一する
- リストマーカーはファイル内で統一する（`-` を推奨）

### markdownlint で無効化しているルール

| ルール | 理由 |
|---|---|
| MD013（行の長さ制限） | 日本語テキスト・テーブルでは行長制限が実用的でないため |
| MD025（単一H1） | アーカイブ文献要約など `#` で大セクションを区切る構造を許容 |
| MD028（引用ブロック内空行） | 独立した引用を空行で区切る記法を許容 |
| MD036（強調の見出し利用禁止） | `**①手順名**` や `**【カテゴリ名】**` は意図的な強調であり見出しではない |
| MD060（テーブルスタイル） | パイプ周囲のスペース強制は日本語テーブルで非実用的 |

### markdownlint でカスタム設定しているルール

| ルール | 設定内容 | 理由 |
|---|---|---|
| MD024（見出し重複禁止） | 同一セクション内のみ禁止 | 異なるセクションでの同名見出し（「概要」等）を許容 |
| MD033（インラインHTML禁止） | `<br>`, `<sup>`, `<sub>`, `<details>`, `<summary>` を許可 | テーブル内改行・脚注で使用するため |

## 15. 実装前後チェックリスト（必須）

以下は、AI実装・手動実装のどちらでも**コミット前に必ず確認**する。

### 15.1 実装前チェック

- [ ] 関連ドキュメント（少なくとも `docs/02_methods/CodingRule.md` と対象手法仕様）を再確認した
- [ ] 入出力パスは相対パスで設計し、`pathlib.Path` を使う方針にした
- [ ] 関数責務を分割し、1関数1責務の構成を決めた

### 15.2 実装後チェック

- [ ] `ruff check` と `ruff format` を実行し、エラー・差分がないことを確認した
- [ ] 変数名・関数名・定数名が命名規則に従っている（日本語変数名を使っていない）
- [ ] 追加・変更した関数に型ヒントと日本語docstringを付与した
- [ ] 複雑な処理に日本語コメントを付与した（過不足なく簡潔に）
- [ ] 例外処理を実装し、エラーメッセージが日本語で理解しやすい
- [ ] 再現性に影響する設定（パス、乱数、閾値）を明示した
- [ ] 不要なコード・未使用変数・デバッグ出力を残していない

### 15.3 出力前チェック

- [ ] 変更ファイルを自分で読み返し、規約違反がないことを確認した
- [ ] 主要ファイルの静的エラー（LSP/構文エラー）を確認した
- [ ] 変更内容を説明する際、根拠となるファイルを明示できる状態にした
- [ ] ドキュメントを追加・改名した場合は `docs/README.md` を更新した
- [ ] `environment.yml` を更新した場合は `docs/setup.md` も確認した
- [ ] `.gitignore` や生成物方針を更新した場合は `docs/02_methods/data_management_guide.md` も確認した

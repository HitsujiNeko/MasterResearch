# ローカル自動レビュー ＋ PR 作成

task-workflow.md「5. タスク完了」の substep **③ ローカル自動レビュー ＋ push・PR作成** を担うコマンド。承認ゲート③（完了条件・PR本文案のレビュー）を通過した後に実行する。

push・PR作成に**先立って**レビュー用サブエージェントを起動し、**現在のブランチ全体（クロスコミット）をローカルでレビュー**する。指摘への対応（採否確認・修正）を終えてから push ＋ `gh pr create` を行う。

> **原則**: レビュー結果は**メイン会話に返すのみ。GitHub の PR には一切投稿しない**（外部書き込みを行わない）。PR コメント欄での `/coderabbit`（外部レビュー）との二重投稿を避けるためであり、両者は観点が異なる相補的なレビューである。push前にローカルレビューの指摘対応を終えることで、CodeRabbit は常にローカルレビュー済みの最終コードのみをレビューする（push後にレビューすると、指摘対応の追加pushとCodeRabbitの初回レビューがずれる問題を避ける）。

## Step 1: 適用範囲の判定

| 状況 | レビューの扱い |
|---|---|
| **Tier 1 並列タスク** | 自動レビューは**必須**。要否確認なしで Step 2 以降を実行する |
| **単一タスク／Tier 2 並列タスク** | push前に「ローカル自動レビューを実行してよいか」をユーザーに確認する。不要と回答された場合は Step 2・3 をスキップし Step 4（push＋PR作成）のみ実行する |

（つまり **Tier 1 並列タスクのみ必須**で、それ以外はすべて要否をユーザーに確認する。）

## Step 2: レビュー用サブエージェントの起動（push前）

push・PR作成に**先立って**、Agent ツールでレビュー用サブエージェント（汎用エージェント）を起動する。サブエージェントには以下を指示する。

- **対象**: 現在の作業ブランチを**最新のリモート `main`** と比較した**フル差分**（＝ブランチ上の全コミット。クロスコミットのレビュー）。レビュー前に `git fetch origin main` で最新化する。**fetch が失敗した場合はレビューと後続のpushを中断し、再実行またはユーザー確認に進む**（失敗を無視して古いリモート追跡ブランチのまま比較すると、最新の `main` との差分を見落とすため）。成功後に three-dot の `git diff origin/main...HEAD`（merge-base 基準＝分岐点以降のブランチ側変更のみ）を用いる。ローカル `main` は古い可能性があるため基準に使わない。two-dot（`..`）も `main` 側の無関係な変更を含み得るため使わない。**この差分取得は対象ブランチ自体を push していなくても行える**（比較対象はリモートの既存 `main` であり、レビュー対象ブランチの push は不要なため）
- **観点**: バグ・正確性・研究ドメイン前提（CRS・単位°C・有効カバレッジ等）・簡潔化・効率
- **出力**: **深刻度順の箇条書き**（高 → 低）。各項目に「対象ファイル:行・内容・根拠」を含める
- **禁止**: GitHub への書き込みを一切行わない（`gh` によるレビュー投稿・PR コメント・ステータス変更などの外部書き込み禁止）

> **なぜビルトイン `/review` を直接使わないか**: ビルトイン `/review` は GitHub PR へレビューを投稿する用途であり、本コマンドの「PR に投稿しない」原則と衝突する。そのため、投稿を伴わないローカルレビュー（ビルトイン `/code-review` と同じ観点・範囲）をサブエージェントに実行させる。

サブエージェントの最終報告はメイン会話へ自動で返るため、レビュー結果がメインセッションのコンテキストに取り込まれる。

**失敗時の扱い（成功扱いにしない）**: Agent の起動失敗・タイムアウト・**空の最終報告**は、レビュー成功とみなさない。失敗をメイン会話に明示したうえで、

- **Tier 1 並列タスク**（レビュー必須）: 後続工程（Step 4 の push・PR作成 以降）に進まず、**再実行するかユーザーの判断を仰ぐまで停止**する
- **単一タスク／Tier 2**: 失敗を報告し、レビュー再実行の要否をユーザーに確認する

## Step 3: 指摘への対応

サブエージェントから返った所見を、**深刻度順の箇条書き要約**としてメイン会話に提示する。指摘なし、または全て却下の場合はそのまま Step 4（push＋PR作成）へ進む。Tier 1 で却下した指摘は、理由とともにPR作成後に報告する。

- **Tier 1 並列タスク**: parallel-workflow.md の「中間承認なしで PR 作成まで実行する」原則に従い、**採否確認を待たず自律的に対応する**。妥当と判断した指摘のみ修正し、修正が**軽微でない場合**（typo・lint対応等ではない場合）はレビュー用サブエージェントを**再実行**して指摘が解消されたことを確認してから Step 4 へ進む。対応した指摘・却下した指摘（あれば理由）は、Step 4 の PR 作成後にユーザーへ報告する
- **単一タスク／Tier 2 並列タスク**: 指摘の採否はユーザーが判断する（`/coderabbit` と同様の位置づけ）。**承認された指摘のみ**を修正する。修正が**軽微でない場合**は、修正後にレビュー用サブエージェントを**再実行**し、指摘が解消されたことを確認してから Step 4 へ進む（task-workflow.md の段階的コミットにおける再セルフレビューの扱いに準じる）
- 修正はコミット単位を意味のあるまとまりに分けてコミットする（task-workflow.md の段階的コミットに準じる）

## Step 4: push ＋ PR 作成

レビュー指摘への対応完了後（または指摘なし・レビュー省略の場合）に実行する。承認ゲート③を通過していることが前提。

```bash
git push -u origin {Issue番号}/{タスク要約英文}

# 重複PR防止: 同一 head の既存PRを確認し、あれば再利用する
pr_url="$(gh pr list --head {Issue番号}/{タスク要約英文} --state open --json url --jq '.[0].url')"
if [ -n "$pr_url" ]; then
  echo "既存PRを再利用: $pr_url"
else
  gh pr create --title "{type}: {変更内容の要約} (#{Issue番号})" --head {Issue番号}/{タスク要約英文} --body-file {PR本文ファイル}
fi
```

- **再実行時の重複PR防止**: `gh pr create` がタイムアウト・部分失敗した後に本コマンドを再実行すると、同一ブランチに重複 PR を作成する恐れがある。`gh pr create` の前に必ず同一 head の既存 PR を確認し、**存在すればそのPRの番号・URLを再利用**して新規作成しない
- `--head` を必ず明示する（意図しないブランチが head になることを防ぐため）
- PR タイトルは `{type}: {変更内容の要約} (#{Issue番号})` の形式に統一する
- 作成された（または再利用する）PR の番号・URL を控える

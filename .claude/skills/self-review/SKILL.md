# セルフレビュースキル

実装後・コミット前に、実装者以外の視点で変更の妥当性を点検する。段階的コミットにおける
レビュー提示（承認ゲート②）の直前に**コミット単位で実行**し、所見をレビュー提示に同梱する。

## 棲み分け（重要・冒頭で必ず確認する）

本スキルは以下の2点に**特化**し、他のレビュー手段と役割を重複させない。

| 手段 | 担当範囲 | 本スキルとの関係 |
|---|---|---|
| **本スキル `/self-review`** | ①自動検出不可のプロジェクト固有規約 ②テストが保証していない範囲 | 本スキルの守備範囲 |
| `/code-review`（ビルトイン） | 汎用的なバグ・簡潔化・効率（手元の作業差分が対象） | ここには踏み込まない（委譲） |
| `/coderabbit` | 外部レビュー（CodeRabbit）の指摘への対応 | ここには踏み込まない（委譲） |
| `ruff` / `markdownlint` | 機械的に検出できる規約（PEP 8・import 順・記法統一等） | 前提（機械保証済みは再点検しない） |

汎用的なバグ・効率・簡潔化を洗いたい場合は `/code-review`、外部レビュー対応は `/coderabbit` を使う。
本スキルは「コミット前の自己点検（固有規約＋テスト非保証範囲）」に限定する。

## 責任分界

- 本スキルは**指摘の洗い出しと分類提示まで**を担う。**修正の実施はユーザー承認後**とし、
  段階的コミットのゲート②と整合させる。
- 指摘の採否・修正方針・学術的妥当性の最終判断は研究者が行う。スキルは断定しない。

点検項目の正本は [CodingRule.md](../../docs/02_methods/CodingRule.md) の
「セルフレビューで確認する項目（自動検出不可）」および「15. 実装前後チェックリスト」。
本スキルはこれを土台に「観点の適用手順」と「テスト非保証範囲の洗い出し方」を提供する。
点検セクションの詳細項目・所見出力テンプレートは [reference.md](reference.md) を参照する。

## 実行手順

以下のチェックリストをコピーして進捗を追跡する:

```text
- [ ] Step 1: 対象差分の把握
- [ ] Step 2: 自動検出不可のプロジェクト固有規約の点検
- [ ] Step 3: 変更差分の妥当性の点検
- [ ] Step 4: テスト保証範囲の点検
- [ ] Step 5: 所見の出力（分類つき提示）
```

### Step 1: 対象差分の把握

このコミット単位で変更したファイル・差分を把握する。

- `git status --short` と `git diff`（未ステージ）・`git diff --staged`（ステージ済み）で変更範囲を確認する
- 変更ファイルを Python / Markdown / 設定などの種別に分ける（Python が無ければ Step 2 の一部は非該当）
- **軽微なコミット**（typo 修正・lint 対応・単純なリネーム等）のみの場合は、本スキルをスキップしてよい
  （task-workflow.md の「軽微コミットはまとめて提示可」ルールと整合）

### Step 2: 自動検出不可のプロジェクト固有規約の点検

`ruff`・`markdownlint` で機械保証されない、CodingRule.md 由来の規約を点検する。
詳細な項目リストは [reference.md](reference.md) の「1. 自動検出不可のプロジェクト固有規約」を参照する。

主な観点（Python）:

- コメント・docstring が日本語で、必須箇所（追加・変更した関数）に付与されているか
- 日本語変数名を使っていないか（コメント・docstring は日本語、識別子は英語スネークケース）
- ファイルヘッダーが module docstring 形式に一本化されているか
- 研究データの絶対パスをハードコードしていないか（外部ツール探索パスの許容は CodingRule.md 7章）
- 再現性（乱数シード・相対パス・`pathlib.Path`）が担保されているか

### Step 3: 変更差分の妥当性の点検

- 変更が Issue の要件・完了条件に対応しているか（要件との突き合わせ）
- 要件外の想定外な変更（無関係なファイル・設定・デバッグ出力の残存）が混ざっていないか
- 共通化すべきロジックを `src/common/` に配置するプロジェクト構成規約に沿っているか
  （**汎用的な重複コード検出は `/code-review` の担当**。ここでは配置規約への適合のみを見る）

### Step 4: テスト保証範囲の点検（独立セクション）

**「テスト通過＝正しい」ではない**という前提で、テストが保証**していない**範囲を明示的に洗い出す。
詳細な洗い出し観点は [reference.md](reference.md) の「テスト保証範囲の点検」を参照する。

洗い出す対象:

- テストが検証していない入力（想定外の型・空・欠損・巨大データ）
- 境界値・異常系（範囲外・不正値・例外経路）
- 副作用（ファイル出力・状態変更・外部サービス呼び出し）の検証有無
- 暗黙の前提条件（呼び出し順序・事前状態）
- **研究ドメイン固有の前提**: CRS（EPSG:4326 基準・投影座標の使い分け）、単位（LST は必ず °C）、
  有効カバレッジ（ROI 全体と同一視しない）等がテストで担保されているか

各項目は「テスト通過が担保していないこと」として言語化し、リスクの高さを添える。

### Step 5: 所見の出力（分類つき提示）

点検結果を **「指摘一覧＋分類」** 形式でユーザーに提示する。分類は次の3段階:

| 分類 | 意味 |
|---|---|
| **対応要** | 規約違反・要件未達・明確なリスク。修正を推奨 |
| **任意** | 改善余地はあるが必須ではない。判断はユーザーに委ねる |
| **対応不要** | 点検した結果、問題なしと確認できた観点（網羅性の明示） |

出力テンプレートは [reference.md](reference.md) の「所見出力テンプレート」に従う。
**修正はここでは実施しない**。ユーザーが採否を判断し、承認された指摘のみを修正してからコミットする。

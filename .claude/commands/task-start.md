# タスク着手: Issue #$ARGUMENTS

以下のチェックリストをコピーして進捗を追跡する:

```text
- [ ] Step 1: 現在の状態確認（読み取りのみ）
- [ ] Step 2: 単一/並列/再開の判定
- [ ] Step 3: Issue 確認・要件確認
- [ ] Step 4: ステータス更新・ブランチ作成（ここで初めて書き込み）
- [ ] Step 5: 計画提示（承認ゲート①）
- [ ] Step 6: 実装セッションの選択（このまま実装／別セッション）
```

## Step 1: 現在の状態確認（読み取りのみ）

以下を実行し、結果をユーザーに提示する。

```bash
git status --short
git diff --stat
git log origin/main..HEAD --oneline
current_branch=$(git branch --show-current)
gh pr list --head "$current_branch" --json number,url,state
```

未コミットの変更・未pushのコミット・既存PRがある場合は内容を提示し、どこから作業を再開するかをユーザーに確認する。**状態を推測して自動的にスキップしない。**

計画書（`.github/prompts/active/{Issue番号}_*.plan.md`）の扱いは、現在のブランチによって分ける。

| 現在のブランチ | 指示された Issue の計画書が未追跡で存在 | 扱い |
|---|---|---|
| `main` 以外 | あり | **確認対象としない**。別セッションが作成した計画の再開である可能性があり、判定は Step 2 で行う |
| `main` | あり | **必ず提示し、続行してよいかを確認する**。別セッションが計画済みの Issue に対し、二重に計画書と作業ブランチを作ってしまうため（下記） |

`main` の場合に提示が必要なのは、Step 2 の再開判定がブランチ名の一致（条件2）を前提とするため、`main` にいる限り再開と判定されないからである。計画セッションの後にユーザーが `main` へ戻った状態で `/task-start` を再実行すると、そのまま Step 4・5 へ進み、同一 Issue の 2 つ目の計画書が作られる。これは [task-implement.md](./task-implement.md) が「想定外の状態」として扱う複数ヒットそのものである。

**他の Issue の計画書が残っている場合は、ブランチにかかわらず通常どおり提示する**（別タスクの残骸である可能性があるため）。

## Step 2: 単一/並列/再開の判定

| 現在のブランチ | 着手記録 | 判定 |
|---|---|---|
| `main` | — | **単一実行** → Step 3 へ |
| `main` 以外 | このセッションが当該ブランチの Issue に会話内で着手済み、かつ指示と同じ Issue | **単一実行（継続）** → Step 3 へ |
| `main` 以外 | 着手済みだが指示は別の Issue | **並列実行** → [parallel-workflow.md](../../.github/parallel-workflow.md) の「最初の分岐」で Yes（分岐①）に該当。Tier 1 は方式 A（自動実行）、Tier 2 のみ方式 A／方式 B を選択する |
| `main` 以外 | 着手記録なし・**かつ**下記5条件をすべて満たす | **再開**（別セッションが作成した計画の実装）→ 並列とは判定せず、[`/task-implement {Issue番号}`](./task-implement.md) の実行を案内して停止する |
| `main` 以外 | 着手記録なし（上記に該当しない。新規セッションが他セッションの作業ブランチに遭遇） | **並列実行** → parallel-workflow.md の「最初の分岐」で No（分岐②）に該当。方式メニューは出さず、このセッション自身を worktree で隔離して着手する。他セッションに委ねない |

ブランチ名の一致・不一致だけでは判定せず、「このセッション自身の着手記録」で判定する。

### 再開の判定条件（5条件）

以下を**すべて**満たす場合のみ「再開」と判定する。1つでも欠ける場合は並列実行（分岐②）として扱う。

1. 指示された Issue の計画書が `.github/prompts/active/{Issue番号}_*.plan.md` に存在する
2. 現在のブランチが `{Issue番号}/...` で、指示された Issue 番号と一致する
3. `git log main..HEAD` が空（計画作成後のブランチ固有コミットが無い）
4. 作業ツリーがクリーン（計画書の未追跡を除く）
5. このセッション自身の着手記録が無い

条件3 の基準は `origin/main` ではなく**ローカルの `main`** とする。作業ブランチは `main` から作成されるため `main..HEAD` は分岐点以降のコミットのみを返すが、`origin/main..HEAD` はローカル `main` に未 push のコミットがあるとそれらを含んでしまい、**ブランチ自身のコミットが 0 でも非空**になる。その場合、再開が並列と誤判定され worktree が作成されるうえ、共有ディレクトリに残る未追跡の計画書は新しい worktree に引き継がれない。なお Step 1 が表示する `origin/main..HEAD` は「未 push のコミット」を示すためのもので目的が異なり、基準が違うのは意図的である。

3 を条件に含められるのは、**計画セッションがコミットを 1 つも残さない**ためである（作成するのはブランチと計画書のみ）。中断点が常にクリーンであることが、この判定を機械的に行える根拠となる。

> **実装が途中まで進んだ状態からの再開は、この5条件を満たさない**（条件3が偽になる）。これは意図した役割分担であり、本ガードは「計画直後に誤って `/task-start` を実行した場合の安全網」に位置づける。途中再開の正規の入口は `/task-implement` であり、そちらを直接実行すれば本ガードを経由しない。

## Step 3: Issue 確認・要件確認

1. `gh issue view $ARGUMENTS` で本文・完了条件・ステータスを確認する
2. 前提としているファイル・関数・ディレクトリが現在のコードベースに存在するか確認する
3. 前提 Issue のステータスを確認する（未完了なら着手可否をユーザーに確認）
4. 曖昧な要件があればユーザーに確認する
5. **問題なしの場合も、確認結果を明示的に報告する**

ステータスが「保留」の場合は「再開しますか？」と確認してから進める。

## Step 4: ステータス更新・ブランチ作成

ユーザーの着手確認が取れてから実行する（**セッション開始だけでは外部状態を変更しない**）。

1. Project ステータスを「進行中」に更新し、開始日（当日）を設定する（GraphQL。ID は `.claude/skills/issue-create/reference.md` を参照）
2. `main` から作業ブランチを作成・チェックアウトする:

   ```bash
   git checkout main && git pull
   git checkout -b {Issue番号}/{タスク要約英文}
   ```

   （並列実行の場合は worktree 内で作成。parallel-workflow.md 参照）

ブランチ命名は `{Issue番号}/{タスク要約英文}`（英語 kebab-case）。既にステータスが「進行中」の場合は変更しない（複数セッション対応）。

## Step 5: 計画提示（承認ゲート①）

- **計画書を作成するタスク**（複数ファイルにまたがる変更・設計判断を伴う変更）: `.github/prompts/active/{Issue番号}_{task_name}.plan.md` を作成し、セルフレビュー後にユーザー承認を得る。**セクション構成・ファイル名は [task-workflow.md](../../.github/task-workflow.md) の「命名規則 → 計画書」を正本とする**（ここでは再掲しない）
- **軽微なタスク**（ドキュメント改訂・設定変更のみ）: 計画書は作らず、方針を口頭提示して確認を得る

## Step 6: 実装セッションの選択（ゲート①の承認後）

計画が承認されたら、「**このまま実装**」「**別セッションで実装**」を選択する。承認前ではなく後に置くのは、分割の要否が計画の中身を見て初めて判断できるためである。位置づけ・適用範囲は [task-workflow.md](../../.github/task-workflow.md) の「計画セッションと実装セッションの分割（任意）」を正本とする。

Claude は以下を観測し、**推奨を添えて**提示する。決定はユーザーが行う。

- 成果物一覧が 3 ファイル以上
- コミット単位が 3 つ以上に分かれる見込み
- 計画作成時のコードベース探索が広範だった

**1 つ以上に該当する場合は「別セッションで実装」を推奨する**（該当数が多いほど推奨を強める）。ただしこれは推奨の閾値であり、決定はユーザーが行う。

| 選択 | このセッションの動作 |
|---|---|
| このまま実装 | [task-implement.md](./task-implement.md) の「同一セッション継続」の入口（Step 3）へ進む |
| 別セッションで実装 | ブランチと計画書を残して**停止**し、新しいセッションでの `/task-implement {Issue番号}` の実行を案内する |

いずれの選択も、計画書の「決定事項」に記録する。

**軽微なタスク**（計画書を作らない）はこの選択の対象外とし、[task-implement.md](./task-implement.md) の Step 3（段階的コミット）へ直接進む。

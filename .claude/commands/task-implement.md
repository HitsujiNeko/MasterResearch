# タスク実装: Issue #$ARGUMENTS

実装フェーズ全体を担うコマンド。計画書の読み込みから段階的コミット（承認ゲート②）、完了条件の確認と PR 本文案の提示（承認ゲート③）までを行い、[create-pr.md](./create-pr.md) に引き継ぐ。**push・PR 作成は本コマンドの責務ではない。**

> **適用範囲**: 本コマンド自体は**並列タスク（worktree 内）でも使用できる**。ただし**セッション分割（＝下記「再開」の入口）の対象は共有ディレクトリの単一実行タスクに限り**、worktree で隔離した並列タスクは対象外とする。根拠は [task-workflow.md](../../.github/task-workflow.md)「計画セッションと実装セッションの分割（任意）」を正本とする。

## 入口

| 入口 | 状況 | 開始位置 |
|---|---|---|
| **再開** | 別セッションで作成された計画書を引き継いで実装する | Step 1 から |
| **同一セッション継続** | `/task-start` のゲート①承認直後にそのまま実装へ入る | Step 3 から（状態・計画をこのセッションが把握済みのため） |

判定は「**このセッション自身が計画を作成したか**」のみで決まる。推測を要する判断は含まない。

> **実装が途中まで進んだ状態からの再開も「再開」に含む。** `/task-start` の再開ガードは「ブランチ上にコミットが無い」ことを条件とするため、この状態は `/task-start` からは並列（worktree 隔離）と判定される。これは矛盾ではなく役割分担であり、`/task-start` のガードは計画直後の取り違えを防ぐ安全網、途中再開の正規の入口は本コマンドである。

以下のチェックリストをコピーして進捗を追跡する:

```text
- [ ] Step 1: 現在の状態確認（再開時のみ・読み取りのみ）
- [ ] Step 2: 計画書の読み込みと陳腐化チェック（再開時のみ）
- [ ] Step 3: 段階的コミット（承認ゲート②）
- [ ] Step 4: 完了条件の確認と PR 本文案の提示（承認ゲート③）
```

## Step 1: 現在の状態確認（再開時のみ・読み取りのみ）

[task-start.md](./task-start.md) の「Step 1: 現在の状態確認」と**同一の手順**を実行する（手順の正本はそちら。ここでは再掲しない）。

加えて、以下を確認する。

- 現在のブランチが `{Issue番号}/{タスク要約英文}` の形式で**指示された Issue 番号と一致する**こと。一致しない場合は実装に入らず、状態を提示してユーザーに判断を仰ぐ
- 計画書は git 未追跡のため `git status` に必ず現れる。**これは再開時の正常な状態であり、判断を仰ぐべき「未コミットの変更」として扱わない**。ブランチ上の未 push コミットも、途中まで実装が進んだ再開では正常な状態である（Step 2 で計画書と突き合わせる）。確認を要するのは、それ以外の未追跡ファイル・作業ツリーの変更・既存 PR である

## Step 2: 計画書の読み込みと陳腐化チェック（再開時のみ）

1. `.github/prompts/active/{Issue番号}_*.plan.md` を読み込む。**存在しない場合は中断**し、`/task-start {Issue番号}` の実行を案内する（セッション分割は計画書のあるタスクに限るため。計画書を作らない軽微なタスクは分割の対象外であり、再開の入口も持たない）
   - **複数ヒットした場合は自分で選ばず**、一覧を提示してどれを使うかユーザーに確認する（同一 Issue の計画書が複数残るのは想定外の状態であり、取り違えると誤った計画で実装に入るため）
2. 計画書の内容（アプローチ・成果物一覧・動作確認手順・決定事項）を要約してユーザーに提示する
3. 以下の**陳腐化チェック**を行い、結果を明示的に報告する（乖離なしの場合も報告する）

   ```bash
   git fetch origin main
   git log HEAD..origin/main --oneline
   ```

   - `main` が計画作成後に進んでいないかを確認する
   - 計画書が前提としているファイル・関数・ディレクトリが現在も存在するかを確認する
   - 乖離があれば内容を提示し、計画の修正要否をユーザーに確認する
   - **`git fetch` が失敗した場合は「乖離なし」と報告しない。** 古いリモート追跡ブランチとの比較になり `main` の進行を見落とすため、失敗を明示したうえで再実行するか、検証できないまま続行してよいかをユーザーに確認する
4. **実装の進捗を突き合わせる**（ブランチ上に既存コミットがある場合）

   ```bash
   git log origin/main..HEAD --oneline
   ```

   - 既存コミットを計画書の**コミット単位**と対応付け、どこまで完了しているかを提示する
   - **未着手の単位から再開する**。完了済みの単位をやり直さず、飛ばしもしない
   - 対応が判然としない場合は自分で決めず、対応表を提示してユーザーに確認する
5. 「決定事項」の**不採用となった代替案**を確認する。一度却下された案を蒸し返さない

`main` が進んでいた場合でも、**rebase・merge を自動で実行しない**。取り込みの要否はユーザーが判断する。

## Step 3: 段階的コミット（承認ゲート②）

[task-workflow.md](../../.github/task-workflow.md) の「3. 実装（段階的コミット）」に従う。サイクル（実装 → lint → セルフレビュー → 所見つきレビュー提示 → 承認 → コミット）・軽微なコミットの扱い・コミットメッセージ形式は、いずれもそちらを正本とする。

## Step 4: 完了条件の確認と PR 本文案の提示（承認ゲート③）

[task-workflow.md](../../.github/task-workflow.md) の「5. タスク完了」の **① 完了条件の確認とレビュー依頼**に従い、共通完了条件と Issue 本文の `## 完了条件` を確認したうえで、PR 本文案とあわせてユーザーに提示する。

**未承認の場合は Step 3 に戻り**、改善事項に対応してから再度提示する（task-workflow.md「5. タスク完了 ②」）。

承認を得たら、PR 本文案を **UTF-8 のファイルに保存**し、そのパスを引数に渡して [create-pr.md](./create-pr.md)（`/create-pr {PR本文ファイル}`）の実行を案内する。保存先・保存が必要な理由は task-workflow.md「5. タスク完了」の「PR 本文案の受け渡し（唯一の定義）」を正本とする。

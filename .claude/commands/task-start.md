# タスク着手: Issue #$ARGUMENTS

以下のチェックリストをコピーして進捗を追跡する:

```text
- [ ] Step 1: 現在の状態確認（読み取りのみ）
- [ ] Step 2: 単一/並列の判定
- [ ] Step 3: Issue 確認・要件確認
- [ ] Step 4: ステータス更新・ブランチ作成（ここで初めて書き込み）
- [ ] Step 5: 計画提示（承認ゲート①）
```

## Step 1: 現在の状態確認（読み取りのみ）

以下を実行し、結果をユーザーに提示する。

```bash
git status --short
git diff --stat
git log origin/main..HEAD --oneline
gh pr list --head {既存ブランチ名} --json number,url,state
```

未コミットの変更・未pushのコミット・既存PRがある場合は内容を提示し、どこから作業を再開するかをユーザーに確認する。**状態を推測して自動的にスキップしない。**

## Step 2: 単一/並列の判定

| 現在のブランチ | 着手記録 | 判定 |
|---|---|---|
| `main` | — | **単一実行** → Step 3 へ |
| `main` 以外 | このセッションが当該ブランチの Issue に会話内で着手済み、かつ指示と同じ Issue | **単一実行（継続）** → Step 3 へ |
| `main` 以外 | 着手済みだが指示は別の Issue | **並列実行** → [parallel-workflow.md](../../.github/parallel-workflow.md) の「セッション中に並列指示を受けた場合」に従う |
| `main` 以外 | 着手記録なし（新規セッションが他セッションの作業ブランチに遭遇） | **並列実行** → parallel-workflow.md の「方式 B」に従い、このセッション自身を worktree で隔離して着手する。他セッションに委ねない |

ブランチ名の一致・不一致だけでは判定せず、「このセッション自身の着手記録」で判定する。

## Step 3: Issue 確認・要件確認

1. `gh issue view $ARGUMENTS` で本文・完了条件・ステータスを確認する
2. 前提としているファイル・関数・ディレクトリが現在のコードベースに存在するか確認する
3. 前提 Issue のステータスを確認する（未完了なら着手可否をユーザーに確認）
4. 曖昧な要件があればユーザーに確認する
5. **問題なしの場合も、確認結果を明示的に報告する**

ステータスが「保留」の場合は「再開しますか？」と確認してから進める。

## Step 4: ステータス更新・ブランチ作成

ユーザーの着手確認が取れてから実行する（**セッション開始だけでは外部状態を変更しない**）。

1. Project ステータスを「進行中」に更新し、開始日（当日）を設定する（GraphQL。ID は `.claude/skills/issue-create/reference.md` を参照）
2. `main` から作業ブランチを作成・チェックアウトする:

   ```bash
   git checkout main && git pull
   git checkout -b {Issue番号}/{タスク要約英文}
   ```

   （並列実行の場合は worktree 内で作成。parallel-workflow.md 参照）

ブランチ命名は `{Issue番号}/{タスク要約英文}`（英語 kebab-case）。既にステータスが「進行中」の場合は変更しない（複数セッション対応）。

## Step 5: 計画提示（承認ゲート①）

- **計画書を作成するタスク**（複数ファイルにまたがる変更・設計判断を伴う変更）: `.github/prompts/active/{Issue番号}_{task_name}.plan.md` を「アプローチ / 成果物一覧 / 動作確認手順」の3セクションで作成し、セルフレビュー後にユーザー承認を得る。計画書はコミット対象外・タスク完了時に削除
- **軽微なタスク**（ドキュメント改訂・設定変更のみ）: 計画書は作らず、方針を口頭提示して確認を得る

承認後、[task-workflow.md](../../.github/task-workflow.md) の「段階的コミット」に従って実装を開始する。

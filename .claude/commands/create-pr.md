# PR 作成 ＋ ローカル自動レビュー

task-workflow.md「5. タスク完了」の substep **③ push・PR作成 ＋ ローカル自動レビュー** を担うコマンド。承認ゲート③（完了条件・PR本文案のレビュー）を通過した後に実行する。

`push` ＋ `gh pr create` に続けて、レビュー用サブエージェントを起動し、**PR 全体（クロスコミット）をローカルでレビュー**して、結果を**深刻度順の箇条書き要約**でメイン会話に取り込む。

> **原則**: レビュー結果は**メイン会話に返すのみ。GitHub の PR には一切投稿しない**（外部書き込みを行わない）。PR コメント欄での `/coderabbit`（外部レビュー）との二重投稿を避けるためであり、両者は観点が異なる相補的なレビューである。

## Step 1: 適用範囲の判定

| 状況 | レビューの扱い |
|---|---|
| **Tier 1 並列タスク** | 自動レビューは**必須**。要否確認なしで Step 2 以降を実行する |
| **単一タスク／Tier 2 並列タスク** | PR 作成前に「作成後にローカル自動レビューを実行してよいか」をユーザーに確認する。不要と回答された場合は Step 2 のみ実行してレビュー（Step 3・4）をスキップする |

（つまり **Tier 1 並列タスクのみ必須**で、それ以外はすべて要否をユーザーに確認する。）

## Step 2: push ＋ PR 作成

承認ゲート③を通過していることを前提に実行する。

```bash
git push -u origin {Issue番号}/{タスク要約英文}

# 重複PR防止: 同一 head の既存 PR を確認し、あれば再利用する
gh pr list --head {Issue番号}/{タスク要約英文} --state open --json number,url

# 既存 PR が無い場合のみ新規作成する
gh pr create --title "{type}: {変更内容の要約} (#{Issue番号})" --head {Issue番号}/{タスク要約英文} --body-file {PR本文ファイル}
```

- **再実行時の重複PR防止**: `gh pr create` がタイムアウト・部分失敗した後に本コマンドを再実行すると、同一ブランチに重複 PR を作成する恐れがある。`gh pr create` の前に必ず同一 head の既存 PR を確認し、**存在すればそのPRの番号・URLを再利用**して新規作成しない
- `--head` を必ず明示する（意図しないブランチが head になることを防ぐため）
- PR タイトルは `{type}: {変更内容の要約} (#{Issue番号})` の形式に統一する
- 作成された（または再利用する）PR の番号・URL を控える

## Step 3: レビュー用サブエージェントの起動

PR 作成の**直後**に、Agent ツールでレビュー用サブエージェント（汎用エージェント）を起動する。サブエージェントには以下を指示する。

- **対象**: 現在の作業ブランチを**最新のリモート `main`** と比較した**フル PR 差分**（＝ブランチ上の全コミット。クロスコミットのレビュー）。レビュー前に `git fetch origin main` で最新化し、three-dot の `git diff origin/main...HEAD`（merge-base 基準＝分岐点以降のブランチ側変更のみ）を用いる。ローカル `main` は古い可能性があるため基準に使わない。two-dot（`..`）も `main` 側の無関係な変更を含み得るため使わない
- **観点**: バグ・正確性・研究ドメイン前提（CRS・単位°C・有効カバレッジ等）・簡潔化・効率
- **出力**: **深刻度順の箇条書き**（高 → 低）。各項目に「対象ファイル:行・内容・根拠」を含める
- **禁止**: GitHub への書き込みを一切行わない（`gh` によるレビュー投稿・PR コメント・ステータス変更などの外部書き込み禁止）

> **なぜビルトイン `/review` を直接使わないか**: ビルトイン `/review` は GitHub PR へレビューを投稿する用途であり、本コマンドの「PR に投稿しない」原則と衝突する。そのため、投稿を伴わないローカルレビュー（ビルトイン `/code-review` と同じ観点・範囲）をサブエージェントに実行させる。

サブエージェントの最終報告はメイン会話へ自動で返るため、レビュー結果がメインセッションのコンテキストに取り込まれる。

**失敗時の扱い（成功扱いにしない）**: Agent の起動失敗・タイムアウト・**空の最終報告**は、レビュー成功とみなさない。失敗をメイン会話に明示したうえで、

- **Tier 1 並列タスク**（レビュー必須）: 後続工程（④ CodeRabbit 対応・⑤ merge）に進まず、**再実行するかユーザーの判断を仰ぐまで停止**する
- **単一タスク／Tier 2**: 失敗を報告し、レビュー再実行の要否をユーザーに確認する

## Step 4: 要約提示

サブエージェントから返った所見を、**深刻度順の箇条書き要約**としてメイン会話に提示する。

- レビュー結果は提示のみとし、対応要否はユーザーが判断する（`/coderabbit` と同様の位置づけ）
- 続く工程（④ CodeRabbit 対応・⑤ squash merge）は task-workflow.md に従う

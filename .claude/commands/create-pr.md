# ローカル自動レビュー ＋ PR 作成

task-workflow.md「5. タスク完了」の substep **③ ローカル自動レビュー ＋ push・PR作成** を担うコマンド。承認ゲート③（完了条件・PR本文案のレビュー）を通過した後に実行する。

push・PR作成に**先立って**、変更区分をブランチの差分パスで検証し、区分で必要とされる場合はレビュー用サブエージェントを起動して**現在のブランチ全体（クロスコミット）をローカルでレビュー**する。指摘への対応（区分 S・D は上限つきの自動修正と再レビュー、区分 R は採否確認と修正）とレビュー実施記録の追記を終えてから push ＋ `gh pr create` を行う。変更区分の定義・区分別のレビュー適用は [task-workflow.md「変更区分（唯一の定義）」](../../.github/task-workflow.md#変更区分唯一の定義)を正本とする（ここでは区分表を再掲しない）。

> **原則**: レビュー結果は**メイン会話に返すのみ。GitHub の PR には一切投稿しない**（外部書き込みを行わない）。PR コメント欄での `/coderabbit`（外部レビュー）との二重投稿を避けるためであり、両者は観点が異なる相補的なレビューである。push前にローカルレビューの指摘対応を終えることで、CodeRabbit は常にローカルレビュー済みの最終コードのみをレビューする（push後にレビューすると、指摘対応の追加pushとCodeRabbitの初回レビューがずれる問題を避ける）。

## Step 1: 変更区分の検証と適用範囲の決定

ローカルレビューを実行するかどうかは**変更区分と Tier で自動的に決まる**。ユーザーに実行の要否を尋ねない。

1. **確定済みの区分を読み取る**: 引数の PR 本文ファイル（ゲート③で承認済み。Tier 1 並列タスクでは Tier 承認時に確定した区分を記入したもの）の「変更区分」欄から、R／S／D のいずれかを読み取る。未記入・複数選択など一意に読み取れない場合は、推測で補わずに停止してユーザーに確認する（Tier 1 × 方式 A は下記の返却に従う）
2. **差分パスで検証する**: `git fetch origin main` で最新化したうえで（**失敗した場合は停止**。古いリモート追跡ブランチとの比較では変更パスを見落とすため）、`python scripts/change_category.py --expect {確定済みの区分}` を実行し、終了コードで分岐する。`python` で起動できない場合（コマンドが見つからない、Windows の Microsoft Store 用スタブが 9009 を返す等で、スクリプトの出力が 1 行も無い場合）は `python3` で再実行する。比較基準は既定の `origin/main...HEAD`、パスの区分表の正本はスクリプトである
   - **0**: 確定済みの区分より重いパスはない。ただし区分 **D** の場合、D はパスではなく変更内容で決まるため、差分の内容が D の定義（挙動・出力を変えない）に収まるかも確認する（スクリプトが「内容確認が必要」と列挙した R のパスを特に確認する）。R パスで識別子・文字列リテラル・ファイル名のリネームがある場合や、挙動を変える変更が含まれる場合は停止する
   - **3**: 確定済みの区分 **S** に対し、R のパスが含まれる。停止する
   - **2**: 実行エラー（比較基準が無い・差分が 0 件など）。区分を検証できないため停止し、エラー内容を提示して原因の解消を待つ（区分の再確定は求めない）。0・2・3 以外の終了コード（Python 自体の起動失敗・構文エラーによる 1 等）も同様に扱う
   - 区分による停止時は、該当するパスと判定した区分（スクリプトの出力）を提示し、**ユーザーに区分の確定をやり直してもらう**。再確定した区分は PR 本文ファイルの「変更区分」欄にも反映する。再確定前のコミットの扱い・ゲート③の取り直しは、正本の判定ルール（区分を重い方へ確定し直した場合）に従う
   - **Tier 1 × 方式 A**（ユーザーに問い合わせられないエージェント）では、区分欄を読み取れない場合も含め、PR を作成せずに該当パスと判定した区分をメインセッションへ返して停止する（以降の扱いは正本の判定ルールに従う）
3. **適用範囲を決める**:

| 状況 | ローカルレビュー |
|---|---|
| **Tier 1 並列タスク** | 区分によらず**必須**（区分 D でも省略しない） |
| 単一タスク／Tier 2 並列タスクで区分 **R** | **必須** |
| 単一タスク／Tier 2 並列タスクで区分 **S** | **必須**（Step 2 の観点に固有規約等を含める） |
| 単一タスク／Tier 2 並列タスクで区分 **D** | 省略する。Step 2・3 をスキップして Step 4（レビュー実施記録の追記）へ進む |

## Step 2: レビュー用サブエージェントの起動（push前）

push・PR作成に**先立って**、Agent ツールでレビュー用サブエージェント（汎用エージェント）を起動する。サブエージェントには以下を指示する。

- **対象**: 現在の作業ブランチを**最新のリモート `main`** と比較した**フル差分**（＝ブランチ上の全コミット。クロスコミットのレビュー）。レビュー前に `git fetch origin main` で最新化する。**fetch が失敗した場合はレビューと後続のpushを中断し、再実行またはユーザー確認に進む**（失敗を無視して古いリモート追跡ブランチのまま比較すると、最新の `main` との差分を見落とすため）。成功後に three-dot の `git diff origin/main...HEAD`（merge-base 基準＝分岐点以降のブランチ側変更のみ）を用いる。ローカル `main` は古い可能性があるため基準に使わない。two-dot（`..`）も `main` 側の無関係な変更を含み得るため使わない。**この差分取得は対象ブランチ自体を push していなくても行える**（比較対象はリモートの既存 `main` であり、レビュー対象ブランチの push は不要なため）
- **観点**: バグ・正確性・研究ドメイン前提（CRS・単位°C・有効カバレッジ等）・簡潔化・効率
  - **区分 S の場合は**、[CodingRule.md](../../docs/02_methods/CodingRule.md) の「セルフレビューで確認する項目（自動検出不可）」・「15. 実装前後チェックリスト」と、テストが保証していない範囲（未検証の入力・境界値・異常系・副作用）を観点に加える（区分 S では `/self-review` を省略するため、その点検範囲をここで引き継ぐ）
- **出力**: **深刻度順の箇条書き**（高 → 中 → 低）。各項目に「深刻度・対象ファイル:行・内容・根拠」を含める。深刻度は次の 3 段階とし、Step 3 の停止条件はこの「高」の件数で判定する。停止判定にはサブエージェントが付けた深刻度をそのまま用い、メインセッションは付け直さない（妥当でないと判断した指摘は、理由を明示した却下として扱う）。所見に深刻度が付いていない、または 3 段階以外の尺度で付いている報告は判定に使えないため、下記の失敗時の扱いに従う

  | 深刻度 | 目安 |
  |---|---|
  | 高 | そのまま merge すると実害が出るもの（誤動作・データ破損・規約違反・文書間の矛盾・承認ゲートや push 条件の迂回・研究ドメイン前提（CRS・単位°C・有効カバレッジ等）の違反） |
  | 中 | 実害は限定的だが直すべきもの（誤読を招く曖昧な記述・境界値や異常系の未処理・テストの不足） |
  | 低 | 表記・簡潔化・好みの範囲 |

- **禁止**: GitHub への書き込みを一切行わない（`gh` によるレビュー投稿・PR コメント・ステータス変更などの外部書き込み禁止）

> **なぜビルトイン `/review` を直接使わないか**: ビルトイン `/review` は GitHub PR へレビューを投稿する用途であり、本コマンドの「PR に投稿しない」原則と衝突する。そのため、投稿を伴わないローカルレビュー（ビルトイン `/code-review` と同じ観点・範囲）をサブエージェントに実行させる。

サブエージェントの最終報告はメイン会話へ自動で返るため、レビュー結果がメインセッションのコンテキストに取り込まれる。Step 3 の再レビューも、同じ指示で（修正後のブランチを対象に）サブエージェントを起動し直して行う。

**失敗時の扱い（成功扱いにしない）**: Agent の起動失敗・タイムアウト・**空の最終報告**・**深刻度を判定できない報告**は、レビュー成功とみなさない。本コマンドがレビューを実行するのは必須の場合に限られるため、失敗は Tier・区分によらず同じ扱いとする。失敗をメイン会話に明示したうえで、後続工程（Step 5 の push・PR作成 以降）に進まず、**再実行するかユーザーの判断を仰ぐまで停止**する。

## Step 3: 指摘への対応

サブエージェントから返った所見を、**深刻度順の箇条書き要約**としてメイン会話に提示する。対応は確定済みの変更区分で分かれる。**区分 S・D は「レビュー → 修正 → 再レビュー」を上限つきで反復**し、**区分 R は自動修正しない**。いずれの区分でも、修正はコミット単位を意味のあるまとまりに分けてコミットする（task-workflow.md の段階的コミットに準じる）。

### 区分 S・D: 上限つきの反復

Step 1 の表でレビューが必須となる場合に適用する（区分 D の単一タスク／Tier 2 並列タスクはレビュー自体を省略するため対象外であり、実際に適用されるのは Tier 1 並列タスクの区分 D に限られる）。単一タスク・Tier 1 並列タスク・Tier 2 並列タスクで共通の手順とする。**指摘の採否は Claude が判断し、ユーザーの確認を待たずに進める**。各周の結果（所見・修正・却下とその理由）はメイン会話に表示する。自動修正のコミットはゲート③の承認**後**に生じるため、ゲート③の一括確認の対象外となる。その確認は、PR 作成後の報告（下記）と「5. タスク完了 ⑤」の PR レビュー（squash merge 前）で行う（承認済みの PR 本文とのずれは Step 4 で扱う）。

| 周 | 内容 | 次へ |
|---|---|---|
| 1 周目 | レビュー①の所見を提示し、妥当と判断した指摘を**深刻度によらず全件**修正する。却下した指摘は理由を添えて提示する（Issue の範囲外の指摘は修正せず「範囲外」を理由に却下し、必要なら後続 Issue の候補として報告する） | 妥当な「高」が無く、修正なし／軽微な修正のみ → **停止**。それ以外（妥当な「高」があった、または軽微でない修正をした）→ 2 周目 |
| 2 周目（上限） | Step 2 と同じ指示でサブエージェントを再実行し（再レビュー②）、所見を提示する。②の所見は**自動修正しない**（中・低の軽微な修正のみ可。「高」は軽微であっても修正せず、上限到達として扱う） | 妥当な「高」が 0 件 → **停止**。妥当な「高」が残る → **上限到達** |

- **停止条件**: 直近のレビューで妥当な「高」の指摘が 0 件であること（1 周目は加えて、軽微でない修正をしていないこと）。「高」の件数は却下した指摘を除いて数える。「高」を却下した場合は、理由を必ず明示する。停止したら Step 4 へ進む。停止時点で修正していない中・低の指摘は「未対応」として提示する
- **上限**: レビューは**最大 2 回**、自動修正は 1 周目のみとする。2 周目の所見を修正すると、その修正が再レビューで検証されないまま push されるためである。軽微な修正（typo・lint 対応等）は再レビューを要しないため、2 周目でも中・低の指摘に限って行ってよい（「高」を軽微な修正として扱うと、検証されない修正を上限の外で通せてしまうため）
- **上限到達時**: push・PR 作成に進まず、残った「高」の指摘を提示してユーザーの判断を待つ。以降はユーザーの指示に従い、上限を超えて自動で反復しない。**Tier 1 × 方式 A**（ユーザーに問い合わせられないエージェント）では PR を作成せず、残った指摘をメインセッションへ返して停止する（[parallel-workflow.md](../../.github/parallel-workflow.md)「失敗時の対応」に従う）
- **自動修正のガード**:
  - 修正後、コミット前に lint を実行し、修正が Python ファイルに及ぶ場合は `pytest` も実行して通過を確認する（pre-commit は pytest を実行しないため、ゲート③で確認したテストの通過が自動修正で崩れないようにする）。通過しない場合、1 周目は修正を続けて通過させてからコミットする（その修正も 2 周目の再レビューの対象となる）。2 周目の軽微な修正で通過しなくなった場合は、その修正を取り消して「未対応」とする（直すと検証されない修正を加えることになるため）
  - 修正のコミット後、Step 1 の区分検証（`python scripts/change_category.py --expect {確定済みの区分}`）を再実行する。結果の扱いは Step 1 と同じとする（区分 D では内容確認を含む）。自動修正が確定済みの区分より重い変更を持ち込んだ場合に、ここで止めるためである
  - `.claude/skills/` に及ぶ修正は自動で行わず、[skill_operation_rules.md](../../docs/02_methods/skill_operation_rules.md) の「変更内容の提示 → 承認 → 実施」に従う。単一タスク／Tier 2 並列タスクではユーザーの承認を待ち、承認されればその周の修正として扱い、見送られた場合は「未対応」として数える。**Tier 1 並列タスク**ではスキル変更が Tier 1 の対象外となる（parallel-workflow.md）。方式 A（ユーザーに問い合わせられないエージェント）は PR を作成せず該当する指摘をメインセッションへ返して停止し、ユーザーに問い合わせられるセッション（分岐②の新規セッション）は以降を Tier 2 として扱い、ユーザーの承認を待つ
- **報告**: 自動修正のコミット・却下した指摘（理由）・未対応の指摘は、Step 5 の PR 作成後にまとめてユーザーへ報告する（PR のレビュー時に確認できるようにするため）。Tier 1 × 方式 A では、各周の結果もメインセッションへの最終報告に含める

### 区分 R: 自動修正しない

区分 R（結果影響）の修正は研究上の判断を含むため、自動修正の対象にしない。区分 R は Tier 1 の対象外であり、単一タスク／Tier 2 並列タスクのみが該当する。

- 指摘の採否はユーザーが判断する（`/coderabbit` と同様の位置づけ）。**承認された指摘のみ**を修正する。指摘なし、または全て却下の場合はそのまま Step 4 へ進む
- 修正が**軽微でない場合**（typo・lint 対応等ではない場合）は、修正後にレビュー用サブエージェントを**再実行**し、指摘が解消されたことを確認してから Step 4 へ進む（task-workflow.md の段階的コミットにおける再セルフレビューの扱いに準じる）。再レビューの所見も提示までとし、修正するかどうかは再びユーザーが判断する
- 反復はユーザーが主導するため、回数の上限は設けない

## Step 4: レビュー実施記録の追記

Step 3（指摘対応）の完了時点で、PR 本文ファイルの「レビュー実施記録」欄に**実施した事実のみ**を追記する。区分 D でレビューを省略した場合も、省略した旨を記録する。事実の追記のみのため**再承認は不要**とし、追記した内容は Step 5 の前にメイン会話へ表示する。記録対象の定義は task-workflow.md の「変更区分（唯一の定義）」を正本とする。

区分 S・D の自動修正によって、承認済みの PR 本文（変更概要・変更詳細など）の記載が実際の差分とずれた場合は、事実の追記を超える変更となるため、該当箇所の更新案を差分つきで提示し、承認を得てから本文を更新する。ユーザーが更新を見送った場合は、元の本文のまま PR を作成し、ずれを PR 作成後の報告に明示する。**Tier 1 並列タスク**には事前に承認された本文がない（区分欄をエージェントが記入する）ため、本文を差分に合わせて更新し、更新した旨を PR 作成後の報告に含める。

区分 S・D の例:

```markdown
- `/self-review`: 省略（区分 S）
- ローカルレビュー: 2 周（停止理由: 高 0 件）
  - 1 周目: 所見 4 件（高 1／中 2／低 1）→ 修正 3／却下 1
  - 2 周目: 所見 1 件（高 0／中 0／低 1）→ 修正 0／未対応 1
```

区分 R の例:

```markdown
- `/self-review`: 実施 3 コミット（所見 4 件: 採用 3／却下 1）
- ローカルレビュー: 2 周（停止理由: 区分 R・ユーザー判断）
  - 1 周目: 所見 3 件（高 1／中 1／低 1）→ 採用 2／却下 1
  - 2 周目: 所見 0 件
```

- `/self-review` は、区分 R では実施したコミット数と所見の採用／却下件数を、区分 S・D では「省略（区分 X）」と記す。件数は実装セッションの会話から集計する
- ローカルレビューは、見出し行に周数（＝レビューの実施回数）と停止理由を、周ごとの行に所見の件数・深刻度別の内訳・対応を記す。対応は、区分 S・D では修正／却下／未対応、区分 R では採用／却下の件数とする
- 停止理由は「高 0 件」「上限到達（高 n 件残り）」「区分 R・ユーザー判断」のいずれかとする。上限到達後にユーザーの指示で対応した場合は、その対応（例: 「上限到達後: ユーザーの指示で修正 1 件」）を 1 行加える
- 記録対象・把握できない値の扱い・所見本文を記さない点は、正本の「レビュー実施記録」に従う（自動修正の内容も本文には書かず、件数のみとする）

## Step 5: push ＋ PR 作成

レビュー実施記録の追記後に実行する。承認ゲート③を通過していることが前提。

```bash
# 重複PR防止: push より前に、同一 head の既存PRを確認する
pr_url="$(gh pr list --head {Issue番号}/{タスク要約英文} --state open --json url --jq '.[0].url')"
if [ -n "$pr_url" ]; then
  echo "既存PRを再利用: $pr_url"
  # 本文の差分を提示し、本文更新の承認を得てから push する（下記「既存 PR を再利用する場合」）
  git push -u origin {Issue番号}/{タスク要約英文}
  # 本文更新が承認された場合のみ実行する
  gh pr edit {PR番号} --body-file {PR本文ファイル}
else
  git push -u origin {Issue番号}/{タスク要約英文}
  gh pr create --title "{type}: {変更内容の要約} (#{Issue番号})" --head {Issue番号}/{タスク要約英文} --body-file {PR本文ファイル}
fi
```

- **再実行時の重複PR防止**: `gh pr create` がタイムアウト・部分失敗した後に本コマンドを再実行すると、同一ブランチに重複 PR を作成する恐れがある。`gh pr create` の前に必ず同一 head の既存 PR を確認し、**存在すればそのPRの番号・URLを再利用**して新規作成しない
- `--head` を必ず明示する（意図しないブランチが head になることを防ぐため）
- PR タイトルは `{type}: {変更内容の要約} (#{Issue番号})` の形式に統一する
- **既存 PR を再利用する場合**、Step 4 で追記した実施記録は PR 本文に反映されていない。**push の前に**既存の PR 本文との差分を提示し、本文更新の承認を求める。push は承認の有無によらず行い、`gh pr edit {PR番号} --body-file {PR本文ファイル}` による本文更新は承認された場合のみ行う（本文更新は外部書き込みのため承認を要する。更新を見送る判断とコードの push は別の論点であるため、push は止めない）
- 作成された（または再利用する）PR の番号・URL を控える
